# Scheduling API — контракт для фронтенда (Profy-Frontend и Profy-CRM)

**Статус: реализовано на ветке `pro-562-scheduling-backend` — 2026-10-20**
(PRO-562 контракт, PRO-512 модели, PRO-513 доступность, PRO-514 сводка
свободного времени, PRO-560 пятничное напоминание по email). Код:
`app/routers/scheduling.py`, `app/services/scheduling/`,
`app/schemas/scheduling.py`, `app/models/scheduling.py`; тесты —
`tests/integration/test_scheduling.py`. Основание — ТЗ CRM Profile v4.1, §2, §3.9, §4.6, §5.1.

Расписание специалистов — **один источник данных на обе части**: кабинет
специалиста в Profy (экран «Расписание») и CRM (экран «Календарь записи»)
читают и пишут его через этот API. Второй копии расписания нет и не будет
(ТЗ §5.1).

В R0 нет записи клиентов и встреч: только доступность специалистов и её
просмотр. Встречи (запись менеджером, основной созвон, переносы) — R2; там,
где они затронут этот контракт, это помечено **[R2]**.

## 0. Время, сетка, заморозка (прочитать до всего остального)

| Правило | Значение |
|---|---|
| Хранение и передача времени | UTC, ISO-8601 с `Z`: `"2026-10-27T05:00:00Z"` |
| Часовой пояс бизнеса | `Asia/Almaty` (UTC+5, без перехода на летнее время) |
| Даты (`date`, `week_start`, `from`, `to`) | календарная дата **по Алматы**, `YYYY-MM-DD` |
| Неделя | понедельник–воскресенье по Алматы; `week_start` — всегда понедельник |
| Слот | 30 минут, начало на `:00` или `:30` |
| Сетка дня | по умолчанию 08:00–22:00 по Алматы (28 слотов), берётся из `GET /config` |
| Заморозка | сегодня и два следующих дня по Алматы (`freeze_days = 3`) |
| Прошедшее время | слот с `start <= now` не меняется никем |

**Фронт не считает «сегодня» и заморозку по часам браузера.** Источник —
`GET /config` (`today`, `now`, `editable_from`) и флаги `frozen`/`past` у
каждого дня и слота в ответах. Отображение — в Asia/Almaty независимо от
часового пояса устройства.

Пример: в воскресенье 25.10 заморожены 25, 26 и 27 октября; менять можно с
28.10 (среды). Неделя 26.10–01.11 открыта для правки только со среды.

## 1. Роли и доступ

Роли `owner`, `sales_head`, `sales_manager` появляются в PRO-497. Проверки —
на сервере для каждого запроса, не только скрытием UI.

| Роль | Своё расписание | Чужое расписание | Сводка `/free` | Список специалистов |
|---|---|---|---|---|
| `psychologist` (специалист) | читать и править (вне заморозки) | **нет** → 404 | нет → 403 | нет → 403 |
| `owner` | — | читать и править любое, в т.ч. в заморозке, **с причиной** | да, **с именами** | да |
| `sales_head` (РОП) | — | нет → 403 | да, **с именами** (только просмотр) | да |
| `sales_manager` (ОП) | — | нет → 403 | да, **без имён и ID** | нет → 403 |
| `marketer`, `student`, `admin` | — | 403 | 403 | 403 |

403 по роли — тот же ответ, что у остальных ролевых роутов:
`{"detail": "Insufficient role"}` **без `error_code`**. Показывайте
«нет доступа» по статусу 403.

Имя специалиста (`full_name`) — `users.full_name`; задаётся при приглашении
сотрудника (`POST /api/v1/admin/invitations`, поле `full_name`). Если имени
нет, вместо него отдаётся email.

- Специалист обращается к своему расписанию через `me` вместо id. Чужой
  `specialist_id` для специалиста — **404 `specialist_not_found`**, не 403:
  нельзя зондировать чужие id (как у заметок).
- Для `sales_manager` в ответе `/free` **поля `specialists` нет вовсе**
  (не `null`, не `[]`) — это проверяется тестом (критерий П1-08).
- Имена у РОП — допущение ТЗ §9.4; если владелец его не подтвердит,
  `sales_head` начнёт получать ответ как `sales_manager`, без изменения схем.

Префикс — `/api/v1/scheduling`. Auth — тот же JWT Bearer.

| Method | Path | Кто | Назначение |

| GET | `/specialists/{id\|me}/weeks/{week_start}` | специалист (me), owner | неделя: все слоты со статусами |
| PATCH | `/specialists/{id\|me}/availability` | специалист (me), owner | открыть / закрыть интервалы |
| POST | `/specialists/{id\|me}/weeks/{week_start}/copy-previous` | специалист (me), owner | скопировать прошлую неделю |
| GET | `/specialists/{id\|me}/template` | специалист (me), owner | шаблон недели |
| PUT | `/specialists/{id\|me}/template` | специалист (me), owner | сохранить шаблон |
| POST | `/specialists/{id\|me}/weeks/{week_start}/apply-template` | специалист (me), owner | применить шаблон к неделе |
| POST | `/specialists/{id\|me}/weeks/{week_start}/publish` | специалист (me), owner | отметить неделю выставленной |
| GET | `/free` | owner, sales_head, sales_manager | сводка свободного времени для CRM |
| GET | `/settings` | owner | настройки напоминания |
| PUT | `/settings` | owner | изменить настройки |

## 3. Конфигурация

```text
GET /api/v1/scheduling/config
```

**200**:

```jsonc
{
  "timezone": "Asia/Almaty",
  "slot_minutes": 30,
  "day_start": "08:00",          // начало сетки, время по Алматы
  "day_end": "22:00",            // конец сетки (последний слот 21:30–22:00)
  "freeze_days": 3,              // сегодня + 2
  "now": "2026-10-25T07:12:03Z", // серверное время
  "today": "2026-10-25",         // дата по Алматы
  "editable_from": "2026-10-28"  // первая дата, которую специалист может менять
}
```

Кешировать на сессию можно, но `now`/`today`/`editable_from` перечитывать
при открытии экрана и после полуночи по Алматы (или просто брать флаги из
ответа недели).

## 4. Неделя специалиста

```text
GET /api/v1/scheduling/specialists/me/weeks/2026-10-26
GET /api/v1/scheduling/specialists/{specialist_id}/weeks/2026-10-26   # owner
```

- `week_start` не понедельник → **422 `week_start_not_monday`**.
- Возвращаются **все** слоты сетки за 7 дней (7 × 28 = 196), включая
  закрытые — фронту не нужно достраивать сетку.

**200**:

```jsonc
{
  "specialist": {"id": "aaaaaaaa-…", "full_name": "Азат Сейткали"},
  "week_start": "2026-10-26",
  "published": true,
  "published_at": "2026-10-23T14:05:00Z",   // null, если не выставлена
  "days": [
    {
      "date": "2026-10-26",
      "frozen": true,          // день в заморозке
      "past": false,           // весь день уже прошёл
      "slots": [
        {
          "start": "2026-10-26T03:00:00Z",   // 08:00 по Алматы
          "end": "2026-10-26T03:30:00Z",
          "state": "closed",
          "frozen": true,
          "past": false,
          "meeting": null
        },
        {
          "start": "2026-10-26T08:00:00Z",   // 13:00 по Алматы
          "end": "2026-10-26T08:30:00Z",
          "state": "free",
          "frozen": true,
          "past": false,
          "meeting": null
        }
        // … всего 28 слотов в дне
      ]
    }
    // … 7 дней
  ]
}
```

### Состояния слота (`state`)

| `state` | Смысл | Видно менеджеру в CRM |
|---|---|---|
| `closed` | не рабочее время (по умолчанию для любого слота) | нет |
| `free` | специалист открыл слот, слот свободен | да, как «свободно» |
| `booked` | в слоте встреча (запись из CRM, `docs/frontend-crm-api-contract.md` §8) | нет |

Выходной, отпуск, исключение — это просто отсутствие открытых слотов
(`closed`); отдельного состояния нет (ТЗ §4.6 п.7). Состояние «занято (личное)»
(ТЗ §4.6 п.6) убрано решением от 21.10: специалист отмечает только свободное время.

Для `booked` в `meeting` — `{"id", "type": "intro30" | "main60", "status"}`, у
остальных слотов `null`. Карточка передачи — отдельным запросом:

```text
GET /api/v1/scheduling/specialists/{id|me}/meetings?from=2026-10-26&to=2026-11-01
```

**200** — встречи периода по времени: `[{"id", "type", "status", "start", "end",
"handoff": {student_name, age, gender, grade, study_language, russian_level,
family_request, parent_participates, contact, contact_phone, manager_comment,
tariff, consent_at}}]`. Цен и переписки ОП там нет (ТЗ §4.8). Доступ — как к
неделе: специалист (`me`) и владелец.

Слот со встречей специалист не меняет: правка → **409 `slot_booked`**, копия
недели и шаблон его пропускают (`skipped`), а при копировании прошлой недели
такой слот переносится как свободный.

`frozen`/`past` у слота — для специалиста это «нельзя менять». Для `owner`
`frozen` носит информационный характер (он может менять с причиной), `past`
— запрет для всех.

## 5. Изменить доступность

Одним запросом — пакет изменений. Применяется **всё или ничего**: если хоть
один интервал нарушает правила, не меняется ни один.

```text
PATCH /api/v1/scheduling/specialists/me/availability
Content-Type: application/json

{
  "changes": [
    {"start": "2026-10-28T08:00:00Z", "end": "2026-10-28T11:00:00Z", "state": "free"},
    {"start": "2026-10-30T03:00:00Z", "end": "2026-10-30T17:00:00Z", "state": "closed"}
  ],
  "reason": null
}
```

- `start`/`end` — границы интервала; `end > start`, оба кратны 30 минутам,
  внутри сетки одного дня. Интервал разворачивается в слоты по 30 минут.
- `state` — только `free` или `closed` (`booked` ставит запись, не
  этот эндпоинт).
- До 200 изменений в запросе; интервалы в пределах одного запроса не должны
  пересекаться.
- `reason` — строка 3–500 символов, **обязательна для `owner`** при правке
  чужого расписания (иначе **422 `reason_required`**); у специалиста
  игнорируется. Правки `owner` пишутся в журнал (PRO-498).

**200** — затронутые недели целиком, в формате §4:
`{"weeks": [ <Week>, … ]}`. Фронт заменяет ими свой кеш.

### Ошибки

| HTTP | `error_code` | Когда |
|---|---|---|
| 422 | `slot_misaligned` | границы не кратны 30 мин или `end <= start` |
| 422 | `slot_out_of_grid` | интервал выходит за `day_start`–`day_end` или за пределы дня |
| 422 | `changes_overlap` | интервалы в запросе пересекаются |
| 422 | `reason_required` | `owner` правит чужое расписание без `reason` |
| 409 | `slot_in_past` | интервал задевает прошедшие слоты |
| 409 | `slot_frozen` | специалист меняет день в заморозке |
| 409 | `slot_booked` | интервал задевает слот со встречей |
| 404 | `specialist_not_found` | нет такого специалиста / специалист указал чужой id |
| 422 | — | больше 200 изменений или пустой `changes` — стандартная ошибка валидации FastAPI (`detail` — список) |
| 403 | — | роль без доступа (`Insufficient role`) |

Тело ошибок 409/422 по правилам слотов дополнено списком конфликтов, чтобы
подсветить ячейки:

```jsonc
{
  "detail": "Нельзя менять расписание в замороженные дни",
  "error_code": "slot_frozen",
  "conflicts": [
    {"start": "2026-10-26T08:00:00Z", "error_code": "slot_frozen"},
    {"start": "2026-10-26T08:30:00Z", "error_code": "slot_frozen"}
  ]
}
```

`detail` — текст для логов; UI строит сообщение по `error_code` (как везде,
см. `app/errors.py`). Новые коды добавляются в `app/i18n/catalog/api_errors.py`
(ru + kk) и в каталоги фронтов.

## 6. Скопировать прошлую неделю

```text
POST /api/v1/scheduling/specialists/me/weeks/2026-11-02/copy-previous
Content-Type: application/json

{"reason": null}
```

Копирует состояния `free`/`closed` с недели `week_start − 7 дней`
на неделю `week_start`, слот в слот, **заменяя** текущие состояния. Слоты,
которые менять нельзя, пропускаются (не ошибка):

**200**:

```jsonc
{
  "week": { /* Week, §4 */ },
  "skipped": [
    {"date": "2026-11-02", "error_code": "slot_frozen", "count": 28},
    {"date": "2026-11-03", "error_code": "slot_booked", "count": 2}
  ]
}
```

`reason` — как в §5 (обязателен для `owner` на чужом расписании).

## 7. Шаблон недели

Шаблон — повторяющееся расписание по дням недели, без дат. Хранится у
специалиста, применяется явно.

```text
GET /api/v1/scheduling/specialists/me/template
```

**200** (у нового специалиста — все дни пустые):

```jsonc
{
  "days": {
    "1": [{"start": "10:00", "end": "13:00", "state": "free"},
          {"start": "14:00", "end": "18:00", "state": "free"}],
    "2": [{"start": "13:00", "end": "19:00", "state": "free"}],
    "3": [], "4": [], "5": [], "6": [], "7": []
  },
  "updated_at": "2026-10-20T10:00:00Z"   // null, если шаблон не сохраняли
}
```

Ключи `"1"`…`"7"` — понедельник…воскресенье; время — по Алматы, `HH:MM`,
кратно 30 минутам, внутри сетки; `state` — только `free`.
Всё, что не перечислено, при применении становится `closed`.

```text
PUT /api/v1/scheduling/specialists/me/template
Content-Type: application/json

{"days": { … как выше … }}
```

**200** — сохранённый шаблон. Ошибки 422: `slot_misaligned`,
`slot_out_of_grid`, `changes_overlap`. Сохранение шаблона ничего не меняет
в расписании и разрешено в любой день.

```text
POST /api/v1/scheduling/specialists/me/weeks/2026-11-02/apply-template
Content-Type: application/json

{"reason": null}
```

**200** — как у copy-previous: `{"week": …, "skipped": […]}`. Нет шаблона →
**409 `template_empty`**.

## 8. Выставить неделю

```text
POST /api/v1/scheduling/specialists/me/weeks/2026-11-02/publish
```

**200**: `Week` (§4) с `published: true`, `published_at`. Повторный вызов
идемпотентен (дата не меняется).

Важно: **публикация не скрывает и не открывает слоты.** Свободные слоты
видны в CRM сразу после сохранения (ТЗ §4.6 п.8). Публикация — сигнал «я
выставил неделю»: от неё зависят пятничное напоминание (PRO-560) и отметка
«неделя не выставлена» у владельца. Править неделю после публикации можно
по обычным правилам; снять публикацию нельзя.

Неделю, которая целиком в прошлом, опубликовать нельзя →
**409 `slot_in_past`**.

## 9. Список специалистов (owner, РОП)

```text
GET /api/v1/scheduling/specialists?week_start=2026-11-02
```

`week_start` необязателен; по умолчанию — **следующая** неделя (та, которую
специалисты должны выставить к пятнице).

**200**:

```jsonc
{
  "week_start": "2026-11-02",
  "items": [
    {
      "id": "aaaaaaaa-…",
      "full_name": "Азат Сейткали",
      "week_published": true,
      "published_at": "2026-10-30T11:20:00Z",
      "free_slots": 46            // открытых свободных слотов на этой неделе
    },
    {
      "id": "bbbbbbbb-…",
      "full_name": "Лолита …",
      "week_published": false,    // «неделя не выставлена»
      "published_at": null,
      "free_slots": 12
    }
  ]
}
```

Только активные пользователи с ролью `psychologist`, по `full_name`.

### Встречи специалиста: `student_id` и `call`

`GET /specialists/{ref}/meetings` у каждой встречи отдаёт ещё `student_id` —
аккаунт ученика в Profile, когда его привязала ссылка из CRM (`null` до этого), —
и `call`: `"first"` — созвон, который записал менеджер, `"second"` — разбор
отчёта, который назначил специалист (`null` — встреча без сделки или отменена).
Раздел «Созвоны» в кабинете строится на них.

### Перенос и отмена созвона специалистом

`POST /specialists/{ref}/meetings/{id}/reschedule {"start", "reason"}` и
`POST /specialists/{ref}/meetings/{id}/cancel {"reason"}` — свой созвон, до его
начала, с причиной (от 3 символов). Перенесённый созвон остаётся у специалиста:
любое время сетки без наложений на его созвоны, длительность прежняя. Ответ —
новый (или отменённый) `SpecialistMeeting`; старый остаётся отменённым с
причиной, в ленте сделки — `meeting_moved` / `meeting_cancelled`. Ошибки:
`meeting_started`, `meeting_status_invalid`, `slot_taken`, `slot_in_past`,
`slot_misaligned`.

## 10. Свободное время для CRM

```text
GET /api/v1/scheduling/free?from=2026-10-26&to=2026-11-01&duration=30
```

| Параметр | Обязателен | Значение |
|---|---|---|
| `from`, `to` | да | даты по Алматы включительно; `to >= from`, не больше 42 дней (6 недель, хватает на месячный вид) |
| `duration` | нет, по умолчанию `30` | `30` или `60` |
| `specialist_id` | нет | фильтр по специалисту; только `owner`/`sales_head`, у менеджера → 403 |

Правила:

- В ответе **только будущие** слоты (`start > now`) в состоянии `free`.
- `duration=30`: слот попадает в ответ, если свободен хотя бы у одного
  специалиста; `free_count` — у скольких.
- `duration=60`: в ответе — начала 60-минутных окон, где **у одного и того
  же** специалиста свободны два соседних слота; `end = start + 60 мин`;
  `free_count` — число таких специалистов (ТЗ §3.9 п.3, критерий П1-09).
- Заморозка на `/free` не влияет: замороженный день не меняет специалист,
  но занять свободное время в нём можно.
- Слоты отсортированы по `start`; пустые часы не возвращаются.

**200 для `sales_manager`** — без имён и ID:

```jsonc
{
  "from": "2026-10-26",
  "to": "2026-11-01",
  "duration": 30,
  "slots": [
    {"start": "2026-10-28T08:00:00Z", "end": "2026-10-28T08:30:00Z", "free_count": 2},
    {"start": "2026-10-28T08:30:00Z", "end": "2026-10-28T09:00:00Z", "free_count": 1}
  ]
}
```

**200 для `owner` и `sales_head`** — то же плюс `specialists` в каждом слоте:

```jsonc
{
  "from": "2026-10-26",
  "to": "2026-11-01",
  "duration": 30,
  "slots": [
    {
      "start": "2026-10-28T08:00:00Z",
      "end": "2026-10-28T08:30:00Z",
      "free_count": 2,
      "specialists": [
        {"id": "aaaaaaaa-…", "full_name": "Азат Сейткали"},
        {"id": "bbbbbbbb-…", "full_name": "Лолита …"}
      ]
    }
  ]
}
```

Ошибки: **422 `range_invalid`** (`to < from` или больше 42 дней),
**422 `duration_invalid`**, **403** (роль без доступа или `specialist_id` у менеджера).

**[R2]** Для владельца и РОП календарю CRM понадобятся и занятые слоты со
встречами — это будет отдельный `GET /api/v1/scheduling/meetings`, формат
`/free` не меняется. Бронирование — `POST /api/v1/scheduling/bookings`
(атомарное, с автоназначением специалиста, ТЗ §3.9 п.4–5).

## 11. Настройки (owner)

```text
GET /api/v1/scheduling/settings
PUT /api/v1/scheduling/settings
```

```jsonc
{
  "week_reminder_weekday": 5,     // 1 = пн … 7 = вс; по умолчанию пятница
  "week_reminder_time": "18:00"   // по Алматы, кратно 30 мин
}
```

PUT принимает тот же объект, **200** — сохранённые значения, изменение — в
журнал.

Напоминание — письмо (ru/kk по `users.locale` специалиста) со ссылкой на
`{FRONTEND_URL}/psychologist/schedule` — **фронт должен держать экран
«Расписание» по этому пути** (PRO-551). Проверка идёт в процессе API раз в
5 минут (`app/services/scheduling/reminders.py`); одно письмо на специалиста
в неделю, даже если время напоминания потом поменяли. Напоминание (PRO-560) уходит специалисту, у которого к этому
моменту не выставлена следующая неделя; при смене времени срабатывает уже
в новое (критерий П2-08).

Сетка дня (`day_start`/`day_end`) в R0 — константа сервера, не настройка.

## 12. Типовые сценарии

**Специалист выставляет следующую неделю (Profy, экран «Расписание»):**

1. `GET /config` → `editable_from`.
2. `GET /specialists/me/weeks/{next_monday}` → сетка; замороженные дни
   показать заблокированными.
3. Либо `POST …/apply-template`, либо `POST …/copy-previous`, либо
   выделение ячеек → `PATCH /specialists/me/availability`.
4. `POST …/publish` → «Неделя выставлена».

**Владелец правит расписание специалиста в заморозке (Profy):**

1. `GET /specialists?week_start=…` → выбрать специалиста.
2. `GET /specialists/{id}/weeks/{week_start}`.
3. `PATCH /specialists/{id}/availability` с `reason` → 200, запись в журнал.

**Менеджер смотрит свободное время (CRM, «Календарь записи»):**

1. `GET /free?from=…&to=…&duration=30` → ячейки с «свободно: N».
2. Для «Консультации» — `duration=60`.

## 13. Чеклист для реализации (PRO-512/513/514)

- Схемы — `app/schemas/scheduling.py`; ответ `/free` для менеджера — отдельная
  схема `FreeSlotsManagerResponse` без поля `specialists`, выбирается по роли.
- Заморозка и «сегодня» — только через общую tz-утилиту (PRO-501), по дате
  Алматы; тесты на границу суток (23:59/00:00 по Алматы = 18:59/19:00 UTC).
- Пакет изменений — в одной транзакции; конфликтующие слоты собираются все,
  а не первый.
- `error_code` из этого документа — в `app/i18n/catalog/api_errors.py` (ru, kk) — сделано.
- Тесты прав: каждая роль × каждый эндпоинт, прямыми запросами (ТЗ §8).
- Критерии приёмки, которые закрывает R0: П2-04, П2-06, П2-08, частично
  П1-08 (менеджер не получает имён и ID).
