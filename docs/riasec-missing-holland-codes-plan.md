# RIASEC: недостающие Holland-коды — план подбора профессий и привязки к университетам

## Контекст

Каталог `scripts/riasec_professions.py` (144 профессии) использует всего 66
из 120 возможных 3-буквенных Holland-кодов (перестановки 3 из 6 букв
R/I/A/S/E/C). 54 кода не покрыты вообще. Разбор (см. диалог, из которого
родился этот план) показал, что эти 54 кода делятся на:

- **16 "частичных" наборов букв** — одна и та же тройка интересов
  представлена не всеми 6 перестановками. Например набор {C,I,S}: `ICS` и
  `CSI` есть, а `CIS`/`ISC`/`SIC`/`SCI` — нет. Это самый ценный тип
  пробела: студент с такими баллами уже сегодня получает какие-то
  направления под соседний код того же набора, просто менее точные.
- **2 набора отсутствуют полностью** (`ACR`, `ACS`) — под них нет ни одной
  профессии ни в каком порядке букв. **Вне рамок этого плана** — решено не
  форсить профессии под сочетания, для которых сложно подобрать реальный
  аналог (Artistic+Conventional+Realistic/Social).

Набор {C,I,S} отдельно важен: в репозитории есть несмерженный черновик
`docs/riasec-near-tie-career-merge-plan.md` — он разбирает прод-баг, где
пограничный балл (I≈53 / C≈53) у реального студента с профилем
{S,I,C}-топ переключал *весь* топ-10 карьер между порядком S-I-C и S-C-I —
то есть между двумя кодами, которых у нас **вообще нет в каталоге сегодня**.
Тот документ чинит проблему с другой стороны (алгоритм tie-break) и **не
входит в этот план** — здесь закрывается только контентная сторона (сами
направления в базе).

**Объём этого плана:** все 16 частичных наборов (~42 потенциальные новые
профессии). Код, для которого не найдётся реальной специальности в
`university-data/*.py`, — пропускается, не форсится (тот же принцип, что
уже описан в самом `specialty_profession_map.py`: "a program with no clear
professional match should not be force-fit").

Цель, как и для всех существующих 144 профессий: каждая новая профессия
должна (а) появиться в таблице `directions` через
`scripts/seed_riasec_directions.py`, и (б) быть привязана хотя бы к одной
реальной специальности реального казахстанского вуза через
`scripts/specialty_profession_map.py`, чтобы `app/services/university_service.py`
(`join(Program.directions).where(Direction.slug == profession_slug)`) могла
реально найти под неё университет — профессия без вуза не закрывает задачу.

наборов (до AIR/EIR/CEI/IRS), так как именно он снимает симптом из
найденного near-tie документа при том же уровне усилий.

## Метод для каждого нового кода (повторяется до ~42 раз)

1. **Сформулировать профессию** — опираясь на теорию RIASEC (первая буква
   кода доминирует, третья второстепенна) и на казахстанский рынок труда.
2. **Найти реальную специальность-носитель** среди 590 уникальных названий
   специальностей в `university-data/*.py` — либо специальность, которая
   **уже замаплена** на другую профессию и объективно годится для второй
   метки (как уже практикуется — например "Хореография" → хореограф +
   преподаватель искусства), либо одна из специальностей, сейчас не
   попадающих ни под одну профессию.
3. Если ничего не находится — код пропускается.
4. Добавить профессию в `scripts/riasec_professions.py`, в секцию,
   соответствующую **первой** букве кода.
5. Добавить/расширить запись в `SPECIALTY_TO_PROFESSIONS`
   (`scripts/specialty_profession_map.py`) с слагом новой профессии
   (транслитерация — тот же алгоритм `slugify`, что в
   `seed_riasec_directions.py`).

### Уже найденные конкретные кандидаты (проверено по реальному дампу специальностей)

- **CIR** (дешёвый набор, 1 код): специальность "Стандартизация,
  сертификация и метрология" (и вариант "...по пищевой отрасли") уже
  замаплена на `spetsialist-po-standartizatsii-i-sertifikatsii` (код
  `CRI`). Метрология как отдельная профессия — **"Инженер по метрологии"**
  (точные измерения = C, техническая диагностика/калибровка = I, работа с
  оборудованием = R) — реалистичный второй профессиональный выход той же
  специальности, код `CIR`.
- **CIS-набор** (приоритет №1, 4 кода): специальность "Социология" уже
  существует и замаплена на `psiholog-issledovatel` (IES) и
  `mediator-konfliktolog` (SEA). Социологическое исследование — это по сути
  Investigative (методология/анализ) + Social (предмет — общество) +
  Conventional (структурированные опросы/отчётность) — кандидат на третью
  метку **"Социолог-исследователь"**, код `ISC`. Остальные 3 кода набора
  (`CIS`, `SIC`, `SCI`) требуют либо той же специальности под другим углом,
  либо другой специальности из немаппленного списка — нужно проверять по
  каждой отдельно.

Остальные 11 наборов (34 кода) прорабатываются тем же методом отдельно —
не решены заранее в этом документе, так как это уже сама работа, а не её
планирование.

## Технические шаги (когда до этого дойдёт)

1. Правки только в двух файлах: `scripts/riasec_professions.py` (новые
   записи, без правки существующих строк) и
   `scripts/specialty_profession_map.py` (новые/расширенные записи
   `SPECIALTY_TO_PROFESSIONS`).
2. `scripts/riasec_professions.py` уже содержит
   `assert len(PROFESSIONS) == len({p["title"] for p in PROFESSIONS})` —
   ловит дубли заголовков автоматически.
3. **Стоит добавить** `tests/unit/test_specialty_profession_map_integrity.py`:
   ничто сегодня не проверяет, что каждый слаг в
   `SPECIALTY_TO_PROFESSIONS` реально существует среди `PROFESSIONS` —
   опечатка молча уходит в `missing_direction_rows` только во время
   сидирования в докере, а не на код-ревью.
4. Применение — в докере, dev-стек, **в этом порядке** (сидирование
   специальностей резолвит слаги через уже существующие в БД `Direction`
   строки):
   ```
   docker compose exec api python scripts/seed_riasec_directions.py
   docker compose exec api python scripts/seed_kz_universities.py
   ```

## Проверка (когда до этого дойдёт)

- Новый тест целостности слагов (`test_specialty_profession_map_integrity.py`).
- Повторный прогон read-only анализа покрытия специальностей и
  Holland-кодов (тот же метод, что использовался при составлении этого
  плана) — подтвердить прогресс.
- Вывод `seed_riasec_directions.py` / `seed_kz_universities.py` — 0
  `missing_direction_rows` для новых слагов, снижение `unmapped`.
- `docker compose exec api pytest` — полный прогон.
- Ручная проверка на сценарии из near-tie документа (R=43, I=52.9, A=47,
  S=79, E=46, C=53.1) — подтвердить, что для обоих вариантов кода (S-I-C
  и S-C-I) в топ-10 теперь попадают не только "соседи", но и точные
  совпадения (сам tie-break баг при этом остаётся неисправленным — это
  отдельная задача).
- `git review-main` перед PR.

## Открытый вопрос, блокирующий продолжение

После составления этого плана появилось отдельное предложение (от Азата,
провалидировано на реальном пользователе, датасеты O*NET 31.0 + маппинг
141/144 наших профессий — детали вне этого документа) заменить весь
`career_match_score`/`matched_careers` (3-буквенный код + позиционные веса)
на прямое сравнение полного 6-мерного RIASEC-профиля через корреляцию
Пирсона — так делает сам O*NET и рекомендует современная vocational
psychology (Nye/Su/Rounds 2018-2021). Не реализовано, решение не принято.

**Если это будет принято — рамка этого плана становится неактуальной**:
понятие "недостающий 3-буквенный код" перестаёт существовать архитектурно
(при непрерывном сравнении 6D-векторов сравнивать просто больше не с чем
"код" в дискретном смысле). В этом случае вместо охоты за конкретными
кодами из таблицы выше правильнее сразу разметить 6D-векторами (из
`onet_riasec_by_soc.json`, 923 профессии O*NET) как существующие 144
профессии, так и любые новые.

Поэтому: **не начинать реализацию этого плана**, пока не будет принято
решение по предложению Pearson/O*NET — иначе часть работы (профессии,
получившие только 3-буквенный код) придётся переделывать под полный
вектор.

## Не входит в этот план (явно)

- Фикс алгоритма near-tie (`docs/riasec-near-tie-career-merge-plan.md`) —
  отдельная задача.
- Коды `ACR`/`ACS` (полностью отсутствующие наборы) — пропускаются.
- Любой код из 16 наборов, для которого не найдётся правдоподобной
  реальной специальности, — пропускается, не форсится.
