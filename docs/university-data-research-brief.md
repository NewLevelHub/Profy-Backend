# Бриф для ресёрча: недостающие данные по вузам и программам (ProFy)

Источник требований: `TZ_Profi.md`, разделы 20 («Университетский модуль») и 21 («База университетов и актуализация данных»).
Текущее состояние проверено напрямую в БД `profi_db` (таблицы `universities`, `programs`) на 2026-08-17.

Документ самодостаточен — не требует чтения ТЗ, чтобы им воспользоваться.

---

## 0. Формат вывода (важно)

Результат ресёрча должен приходить как JSON-массив объектов, по одному на программу (или на вуз — для блока 3), в структуре, описанной ниже в каждом разделе. **Для каждого факта обязательно указывать `source_url` (прямая ссылка на страницу-источник) и `checked_at` (дата, когда факт проверен)** — без этого факт нельзя будет опубликовать (см. раздел 4).

Если факта нет на сайте вуза или в другом надёжном источнике — не придумывать, не усреднять по похожим программам. Явно писать `null` и, если есть, ссылку туда, где абитуриенту стоит проверить самому.

## 1. Что уже закрыто (не дублировать)

Для 517 из 739 программ в 39 вузах Алматы/Астаны в `Program.requirements` уже есть:
- `exams` — предметная пара ЕНТ (для 281 программы, где нет данных по факту гранта) — официальный норматив МОН РК;
- `min_ent_threshold` — минимальный порог ЕНТ для допуска (те же 281);
- `admission_scores_2026` — реальный проходной балл на грант 2026-2027, по факту зачисления (236 программ, из официального списка грантников).

Это покрывает только пункт 9 карточки программы («Экзамены... пороговые баллы») и частично пункт 19 («Гранты»). Всё остальное ниже — не заполнено.

## 3. Полностью отсутствующий блок: иностранные вузы

ТЗ (21.2) требует **8–12 вузов на каждый регион**: США, Великобритания, континентальная Европа, Азия, Канада — итого 40–60 университетов. Сейчас в базе **0** нероссийских/неказахстанских записей (`SELECT DISTINCT country FROM universities` → только `Казахстан`).

По каждому такому вузу нужен весь состав из раздела 21.1 ТЗ:
название, страна, город, сайт, уровень/рейтинг, направления обучения, программы (по каждой — весь блок раздела 2 выше), язык обучения, стоимость, наличие грантов/стипендий, требования к поступлению, дедлайны, список документов, особенности поступления.

**Приоритет** — сначала направления, которые уже популярны у пользователей ProFy (видно по `profession_slugs` в существующих 739 программах: IT/Computer Science, Business/Management, Engineering, Medicine, Law, Design) — по ТЗ «по каждому направлению из числа популярных должен быть хотя бы один вариант в каждой корзине» (корзины — отдельная тема, см. ниже, но данные нужны уже сейчас).

## 4. Казахстанская специфика (20.7) — отдельно, не про конкретные программы

- **«Болашак»** — условия участия, направления, дедлайны подачи, требования — сейчас нет данных вообще.
- **Локальные олимпиады**, которые засчитываются при поступлении (помимо предметных пар ЕНТ) — нет данных.
- ЕНТ/ҰБТ покрыто частично (см. раздел 1).

## 5. Что research НЕ должен пытаться закрыть (не в его силах)

- **Дата обновления + ссылка на источник как поле в БД** — это не данные, это отсутствующее поле в модели `Program`/`University` (сейчас там только `created_at` на уровне строки, не на уровне факта). ТЗ дважды помечает это «Критично» (п. 20.5.22 и 21.4). Это отдельная инженерная задача (миграция схемы), а не то, что можно получить ресёрчем — но именно поэтому важно, чтобы Gemini возвращал `source_url`+`checked_at` по каждому факту (см. раздел 0) — без этого поля их некуда будет положить осмысленно.
- **Три корзины (амбициозные/реалистичные/запасные)** — это логика подбора, не данные по вузу. Не относится к ресёрчу.
- **Очередь подтверждения в админке** — тоже инженерная задача, не ресёрч.

## 6. Как отдать результат обратно

Один JSON-файл (или несколько по регионам/вузам) со списком объектов вида:

```json
{
  "university_slug_or_name": "...",
  "program_name": "...",
  "requirements_patch": { /* любые поля из раздела 2, только те, что реально нашлись */ },
  "cost_per_year": null,
  "grants": [],
  "deadlines": {},
  "sources": [{"field": "language.min_score", "url": "https://...", "checked_at": "2026-08-20"}]
}
```

Дальше это заводится в базу тем же способом, что и сегодняшние данные — идемпотентным скриптом с diff-превью перед записью, не напрямую.
