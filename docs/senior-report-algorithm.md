# Алгоритм формирования результата теста — старшая группа (14–18)

Технический разбор (с формулами, порогами и указанием файлов) для тех, кто работает
с кодом. Продуктовое описание «человеческим языком», без формул — см.
[`kak-schitaetsya-rezultat.md`](./kak-schitaetsya-rezultat.md), этот документ его не
дублирует, а раскрывает «под капотом».

Точка входа: `app/services/report_service.py::build_report()`.
Всё, что ниже, относится к `AgeGroup.senior` (middle работает почти так же — общий RIASEC-путь,
разница только в подаче текста и наборе вопросов; junior — отдельная ветка на MI, не описана здесь).

## 0. Из чего вообще состоит анкета старшей группы

Три независимых инструмента, отвечены в одном прохождении:

| Блок | Что измеряет | Кол-во | Шкала | Таблица |
|---|---|---|---|---|
| RIASEC | 6 категорий интересов (Holland) | все вопросы junior+middle+senior уровней (`visible_tiers`, `app/services/age_tiers.py`) | 1–5 | `questions` (instrument=`riasec`) |
| Big Five | 5 черт характера (IPIP-NEO-120 Johnson), с фасетами | 120 вопросов | 1–5 | `questions` (instrument=`big_five`) |
| Мотивация | 9 категорий (interest/challenge/helping/freedom/money/recognition/stability/creation/teamwork) | N троек по 3 утверждения (MOST/LEAST) | форс-чойс | `motivation_statements` / `motivation_responses` |

Senior — единственная группа, где мотивация задаётся тройками MOST/LEAST
(`motivation_service.py`); junior/middle отвечают на парные Хартеровские вопросы
(`motivation_pair_service.py`) — другая таблица, другая формула, тот же итоговый шейп
(`{категория: балл}`).

**Гейт завершённости** (`report_service._assert_assessment_complete`): отчёт не начнёт
собираться, пока не отвечены ВСЕ вопросы RIASEC+Big Five (`assessment_shared.likert_*`)
И все тройки мотивации (`motivation_service.total_triplets`). Проверка сделана на бэке
независимо от того, что показывал клиент — иначе гонка между двумя вкладками могла бы
запустить сборку недособранного отчёта.

## 1. RIASEC — из ответов в код интересов

Файл: `app/services/riasec_service.py`.

### 1.1 Сырой балл и нормализация

```
raw[T]       = Σ answer_value  по всем вопросам типа T, на которые ответил студент
normalize[T] = round(raw[T] / (questions_count[T] * 5) * 100, 1)
```

Важно: это **не** «доля от собственного максимума студента» (как было в старом движке),
а доля от **теоретического максимума** для этого типа (ответить на 5 по всем вопросам
этого типа = 100%). Студент физически может не набрать 100% ни по одной категории.

### 1.2 Мета-характеристики (`meta` в `AnalysisResult`)

- **differentiation** = `max(normalize.values()) − min(normalize.values())`.
  Порог **< 25.0** (`report_v2_assembler._FLAT_PROFILE_THRESHOLD`) → профиль считается
  «плоским» (`is_flat_profile=True`) — см. §5.4.
- **consistency** — согласованность топ-2 кодов по гексагону Голланда
  (порядок `R-I-A-S-E-C` по кругу): `distance ≤ 1 → high`, `== 2 → medium`, `> 2 → low`.
- **aversion** — количество явных «нет» (ответ ≤ 2) по каждому типу. Используется как
  дисквалифицирующий сигнал, а не как отдельный балл.

### 1.3 Код студента

```python
top_code(normalize, limit=3)  # напр. ["S", "A", "I"]
```
Сортировка по убыванию балла; при равенстве баллов — по фиксированному порядку
`HOLLAND_ORDER = [R, I, A, S, E, C]` (детерминированный тай-брейк, чтобы одинаковые
проценты не давали случайный порядок в зависимости от порядка строк в БД).

### 1.4 Сильные и слабые стороны — трёхуровневая логика

Не просто «топ-3 по баллу» — это давало ложные срабатывания (пример из комментария в коде:
профиль `I=100 A=100 R=C=E=S=20` раньше протаскивал R в «сильные стороны» просто потому что
он был третьим по рангу, хотя это низкий балл).

1. **Уровень 1** — тип набрал `≥ 70` (`LEVEL_HIGH_MIN`, `app/services/scoring_levels.py`)
   **и** доля явных «нет» по нему `< 0.3` (`_AVERSION_DISQUALIFY_RATIO`). Это реальный сигнал.
2. **Уровень 2** (добираем до `limit=3`, если после шага 1 сторон меньше) — любой оставшийся
   тип `≥ 50` (`LEVEL_MEDIUM_MIN`), aversion уже не проверяется.
3. **Никогда** не берётся тип `< 50` — если сильных сторон набралось меньше 3 (вплоть до нуля),
   отчёт покажет меньше — это не баг, а честность (плоский профиль виден отдельно через
   `differentiation`).

**Слабые стороны** — зеркально: тип `≤ 30` (`LEVEL_LOW_MAX`), топ-3 самых низких, без aversion-фильтра.

### 1.5 План развития

```
reinforce  = до 2 активности на КАЖДУЮ из топ-3 букв кода (TYPE_ACTIVITIES)
compensate = до 2 активности на САМУЮ слабую букву, у которой aversion_ratio < 0.3
             (если явно не любит — не предлагаем «компенсировать» именно это)
```

## 2. Подбор профессий — прямое сопоставление, без ИИ

Файл: `riasec_service.py` (`direction_letter_weight`, `career_match_score`,
`matched_careers`) + `app/models/direction.py` (`holland_code` — 3-буквенный код каждой
профессии в базе, напр. `"SAE"`).

### 2.1 Вес буквы в коде направления

```python
def direction_letter_weight(letter, direction_code):
    position = direction_code.find(letter)
    return 3 - position if 0 <= position < 3 else 0
```
То есть: буква на 1-й позиции направления даёт вес **3**, на 2-й — **2**, на 3-й — **1**,
отсутствует — **0**. Позиционный вес важен: направления «ESC» и «SEC» — это разные веса
для одних и тех же трёх букв (раньше `letter in direction_code` не различало их вообще,
и все анаграммы одного набора букв получали одинаковый score).

### 2.2 Итоговый матч-скор

```python
def career_match_score(user_code, direction_code):
    user_weights = [3, 2, 1]   # вес места студента в ЕГО топ-3
    return sum(w * direction_letter_weight(letter, direction_code)
               for w, letter in zip(user_weights, user_code))
```
Максимум — **14** (когда топ-3 студента дословно совпадает с кодом направления в том же
порядке: `3·3 + 2·2 + 1·1`).

### 2.3 Ранжирование и лимит

```python
matched = [(direction, career_match_score(user_code, direction.holland_code))
           for direction in all_directions]
matched.sort(key=lambda pair: (-score, direction.slug))   # тай-брейк по slug
top10 = matched[:10]
```
Сортировка по всей базе направлений (145 штук на момент этого документа), не только
по тем, что связаны с университетскими программами — это отдельный, более широкий
список; университетские программы уже подбираются ПОД конкретную выбранную профессию
отдельным запросом (см. §7).

### 2.4 Уровни в выдаче

`app/services/report_v2_assembler.py::_tier_for_rank`:

| Ранг | Тег |
|---|---|
| 1 | `strong` |
| 2–3 | `good` |
| 4–10 | `worth_trying` |

Показываются все 10 всегда — и плоскому, и не-плоскому профилю одинаково (продуктовое
решение от 2026-08-17, зафиксировано в комментарии кода): даже при близких баллах ранжирование
всё ещё несёт реальный сигнал, просто с меньшей уверенностью — честность через
дисклеймер в тексте (см. §5.4), а не через урезанный список.

### 2.5 Текст «почему подходит» (`why`)

Не ИИ, отдельная детерминированная функция `build_riasec_careers`:
- Если у направления есть пересечение с **уже провалидированными** сильными сторонами
  студента (§1.4) — называется именно это пересечение, упорядоченное по
  `direction_letter_weight` (сначала буква, которая для ЭТОГО направления главная).
- Если пересечения нет (частый случай при плоском профиле) — берётся одна из
  заготовленных нейтральных формулировок (`NEUTRAL_CAREER_WHY_VARIANTS`), по кругу —
  чтобы 10 карточек подряд не повторяли одно и то же предложение.
- Если два направления получили байт-в-байт одинаковое обоснование — второму
  добавляется отличающий факт: `skills_needed[0]` именно этого направления (факт из
  каталога, не утверждение о студенте).

## 3. Big Five — характер и стиль мышления

Файл: `app/services/bigfive_service.py`.

### 3.1 Сырой балл с обратным ключеванием

Часть пунктов сформулирована «наоборот» (`Keyed.minus`) — их значение инвертируется
**при чтении**, не при хранении:
```
item_score = (6 − answer_value)   если keyed == minus
item_score = answer_value          если keyed == plus
raw[domain] = Σ item_score
```

### 3.2 Коррекция на согласие (acquiescence correction)

IPIP-NEO-120 **не сбалансирован** по ключеванию внутри доменов (N: 17+/7-, E: 18+/6-,
A: 7+/17-, O: 12/12, C: 11/13) — студент, который просто соглашается со всем подряд
(«yea-sayer»), без коррекции получил бы завышенный N и заниженный A чисто из-за стиля
ответов, а не содержания.

```
grand_mean = средний сырой ответ (1–5, ДО инверсии) по ВСЕМ пунктам Big Five, что видел
             студент. Если ответов нет — 3.0 (середина шкалы, коррекция = 0.

shift[domain] = (minus_count[domain] − plus_count[domain]) × (grand_mean − 3.0)

raw_corrected[domain] = raw[domain] + shift[domain]
```
Для сбалансированного домена (`plus == minus`) сдвиг всегда 0. Для студента, который
отвечал ровно по середине шкалы в среднем — тоже 0, независимо от баланса домена.
Считается один раз на весь отчёт (`grand_mean` вызывается один раз, значение
передаётся и в доменный, и в фасетный расчёт — до недавнего фикса вызывался дважды
с одинаковым результатом, см. код-ревью этой ветки).

### 3.3 Нормализация

```
normalize[domain] = round((raw_corrected[domain] − count) / (count × 4) × 100, 1)
```
Пол — `count × 1` (минимум по шкале — 1, не 0, т.к. шкала 1–5), не `count × 0` — иначе
диапазон сжимается/съезжает к верху. Клэмп в `[0, 100]` — коррекция у экстремального
респондента иногда чуть перелетает теоретическую границу.

Фасетный расчёт (`facet_raw`/`facet_normalize`) — та же формула, но по паре
`(domain, facet_index)` вместо одного домена.

### 3.4 «Твой характер» (personality_profile)

```
openness             = normalize["O"]
conscientiousness    = normalize["C"]
extraversion         = normalize["E"]
agreeableness        = normalize["A"]
emotional_stability  = round(100 − normalize["N"], 1)   # инверсия — высокий балл = хорошо
```

**Тиринг ОТНОСИТЕЛЬНЫЙ**, не абсолютный (`bigfive_content.relative_bands`) — популяционных
норм для этого инструмента нет:
```
spread = max(5 значений) − min(5 значений)
если spread < 10.0 (_FLAT_SPREAD):     все 5 черт → "medium"
иначе для каждой черты:
    delta = value − mean(5 значений)
    "high"   если delta ≥ 8.0   (_REL_BAND)
    "low"    если delta ≤ −8.0
    "medium" иначе
```
То есть черта оценивается не по абсолютному проценту, а по тому, насколько она выделяется
на фоне ЧЕТЫРЁХ ОСТАЛЬНЫХ черт этого же студента.

**Важный продуктовый нюанс**: в «сильные стороны» (`strength_phrases`) и в «есть, над чем
поработать» (`build_personality_note`, growth-сторона) идут **только 3 из 5** черт —
`openness / conscientiousness / emotional_stability`. Экстраверсия и доброжелательность
осознанно исключены с обеих сторон: высокий балл по ним не универсально «сила» (зависит от
контекста), а низкий — это темперамент (интроверсия, прямота), а не дефицит, который
«стоит подтянуть». Называть его как зону роста — навязывать студенту, что его нормальный
характер — это проблема.

### 3.5 Стиль мышления

Из 9 категорий TZ_Profi.md посчитаны только 4 — остальные требовали бы теста
способностей, которого в продукте нет (`thinking_style_service.py`, намеренно не
подделывается):

```
creative_think = (facet[O,1] + facet[O,2]) / 2     # Imagination + Artistic Interests
systematic     = facet[C,2]                         # Orderliness
strategic      = facet[C,4]                         # Achievement-Striving
practical      = facet[C,1]                         # Self-Efficacy
```

## 4. Мотивация (MOST/LEAST тройки, только senior)

Файл: `app/services/motivation_service.py`.

Каждая «тройка» — 3 карточки, каждая из СВОЕЙ категории (никогда не повторяется категория
внутри тройки — гарантируется генератором троек, `scripts/motivation_statement_bank.py`,
комбинаторный AG(2,3)-дизайн). Студент отмечает одну как **самую близкую** (MOST), одну —
**самую далёкую** (LEAST), третья остаётся нетронутой.

```
MOST    → +2 очка категории этой карточки
NEUTRAL → +1 очко (не выбранная ни MOST, ни LEAST)
LEAST   → +0 очков
```
Сумма по тройке всегда 3 очка, распределённых по трём разным категориям — гарантия
методологии, не проверяется явно кодом.

```python
top_categories(scores, limit=3)  # тай-брейк — фиксированный CATEGORY_ORDER
```

9 категорий: `interest, challenge, helping, freedom, money, recognition, stability,
creation, teamwork`.

## 5. Сборка текста и финального ответа

### 5.1 Каталог фактов (evidence) — ДО обращения к ИИ

Файл: `app/services/report_narrative_context.py`. Чисто детерминированная функция,
без БД, без ИИ — собирает список **проверенных фактов**, которые дальше разрешено
цитировать (и ИИ, и запасному шаблону):

- Интересы → факт только по буквам из уже провалидированных `strengths` (§1.4), НЕ по
  сырым баллам — если студент технически не прошёл фильтр на «сильную сторону», факт про
  этот тип в каталог не попадает вообще.
- Характер → факт только по чертам с относительным тиром `"high"` (§3.4), т.е. до 5 штук.
- Мотивация → топ-3 категории 1:1 с готовыми фразами.
- Стиль мышления → максимум 2 (`_TOP_THINKING_STYLES`), и только те, что реально `> 0`
  (не «топ-2 из четырёх, что бы ни было» — иначе можно «обнаружить» несуществующий сигнал
  у студента с нулевыми фасетами).
- Из онбординга (`subjects_liked`, `subjects_easy`, свободный текст «увлечения») —
  максимум **2** штуки суммарно (`_MAX_ONBOARDING_STRENGTH_EVIDENCE`), похожие
  увлечения группируются по общим значимым словам, чтобы не плодить 3 карточки из
  «Программирование» / «IT/программирование» / «Робототехника». Специально ограничено
  снизу, чтобы самоописание на онбординге не забило собой факты, реально извлечённые
  тестом.

### 5.2 ИИ (если включён) → валидация → запасной шаблон

Файл: `app/services/report_narrative_service.py`. До 3 попыток (1 + 2 корректирующих
ретрая, где модели дословно цитируется её же прошлая ошибка). Список запрещённых/разрешённых
формулировок и полный разбор правил — уже задокументирован в
[`kak-schitaetsya-rezultat.md`, раздел 4](./kak-schitaetsya-rezultat.md#4-где-во-всём-этом-участвует-ии-и-что-ему-разрешено-писать),
не дублирую здесь. Коротко: ИИ разрешено писать ТОЛЬКО про факты из каталога §5.1, никаких
новых чисел/названий/прогнозов. Любой сбой (ИИ недоступен, не прошёл валидацию 3 раза) →
`report_narrative_fallback.py`, тот же каталог фактов, простыми фразами без ИИ. Отчёт
никогда не остаётся без текста.

### 5.3 Карта интересов (`interest_map`)

В отличие от §1.4 (только провалидированные «сильные стороны»), карта интересов
показывает **все 6** RIASEC-сфер, включая слабые — с уровнем по тем же абсолютным
порогам `70/50/30`:
```python
_level(value):  ≥70 → "high"; ≥50 → "medium"; иначе → "low"
```
Плюс отдельное 1–2-предложное summary самой карты (детерминированное, без ИИ) — называет
ярко выраженные сферы, либо (если «средних» меньше половины всех сфер) — заметные средние,
либо честно говорит, что профиль ровный.

### 5.4 Плоский профиль

`is_flat_profile = differentiation < 25.0`. Список профессий **не укорачивается и не
меняется** — тот же топ-10 (§2.3). Единственное отличие: если у студента есть заполненные
«увлечения» в онбординге, к `summary` добавляется одно предложение, приглашающее
присмотреться к направлениям, связанным с этими увлечениями — потому что при близких
баллах топ-3 кода сам по себе близок к шуму, а самостоятельно указанные увлечения могут
быть точнее.

## 6. Кэш, идемпотентность, гонки

Файл: `report_service.py::build_report`.

1. Redis, ключ на `assessment_id`, TTL 24 часа — ускоритель, не источник истины. Падение
   Redis (на чтении или записи) — просто лог-warning, ответ всё равно строится из БД/генерируется.
2. Если строка `AnalysisResult` уже есть в БД — текст (summary/карточки) читается **как
   есть**, а `careers`/`interest_map`/`personality_notes` пересчитываются заново из
   сохранённых сырых баллов теми же чистыми функциями — ИИ повторно не вызывается никогда.
3. Первая генерация: Postgres `pg_advisory_xact_lock(hashtext(assessment_id))` — сериализует
   параллельные запросы на генерацию ОДНОГО и того же отчёта, так что второй запрос,
   пришедший на долю секунды позже первого, дожидается и читает уже готовую строку вместо
   повторного (дорогого, с вызовом ИИ) прохода. `IntegrityError` на INSERT — резервный
   механизм на случай, если блокировка почему-то не сработала.
4. `AnalysisResult` + флип `Assessment.status → completed` — одна транзакция: не может
   существовать «завершённый» тест без отчёта.

## 7. Что зависит от выбранной цели (goal) — уже ПОСЛЕ портрета

Сам портрет (профиль, сильные стороны, 10 профессий, характер, резюме) — **не зависит**
от цели, считается один раз. От цели зависит только отдельный блок «Фокус под твою цель»
и персональный план — см. подробно
[`kak-schitaetsya-rezultat.md`, раздел 5](./kak-schitaetsya-rezultat.md#5-меняется-ли-сам-результат-если-поменять-цель).
Технически это отдельные сервисы, не часть `build_report`:

- **`app/services/goal_overlay_service.py`** — рендерит блок под конкретную цель
  (`explore` / `profession` / `university` / `unsure`≈`explore`).
- **`app/services/gap_analysis_service.py`** (цель `university`, только senior) — под
  выбранную программу вуза классифицирует каждый ключ `Program.requirements` в
  `gpa / language / exam / portfolio / generic` по ключевым словам, сверяет с
  `Profile.grade` и загруженными артефактами (достижения/хобби/клубы/спорт) студента:
  ```
  readiness_score = round((met×1.0 + in_progress×0.5) / total × 100, 1)
  ```
- **`app/services/university_service.py::search_programs`** — университетские программы
  под КОНКРЕТНУЮ выбранную профессию (не общий топ-10, а `Program.directions` JOIN по
  slug направления), сортировка: `University.ranking` (QS World) → `uniranks_world_rank`
  (KZ-рынок) → имя по алфавиту.
- **`app/services/roadmap_builder.py`** — отдельная, более крупная ИИ-генерация (план на
  1мес/3мес/полгода/год), с явно другим промптом под каждую цель — таблица дословных
  формулировок уже есть в
  [`kak-schitaetsya-rezultat.md`, раздел 5](./kak-schitaetsya-rezultat.md#а-вот-что-меняется-по-настоящему--персональный-план-roadmap).
  За рамками этого документа (он про то, как формируется САМ результат теста).
