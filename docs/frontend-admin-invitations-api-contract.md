# Приглашения сотрудников (психологов и админов) — контракт API для фронтенда

**Статус на 2026-10-07: реализовано.** Админские эндпоинты (§3) — PRO-460
(`app/routers/admin_invitations.py`), публичные (§4) и Google-вход (§5) —
PRO-462 (`app/routers/auth.py`, `app/services/oauth_service.py`); логика —
`app/services/invitation_service.py`. Фронт (PRO-464 — админка, PRO-465 —
страница `/invite`) пишется по этому документу. Если API меняется, документ
обновляется в том же PR.

Доступ к админским эндпоинтам (JWT + роль `admin`, 401/403) — как во всей
админке, см. §1 `docs/frontend-admin-university-api-contract.md`.

## 0. Как это устроено

Админ вводит почту, роль и язык письма → бэкенд создаёт запись приглашения и
отправляет письмо со ссылкой `FRONTEND_URL/invite?token=<token>`.
**Пользователь в `users` при этом не создаётся** — только при принятии:

- по ссылке: страница `/invite` → пароль → `POST /auth/invitations/accept`;
- или входом через Google на приглашённую почту (§5);
- или подтверждением кода неподтверждённого аккаунта на эту почту (§4.3).

Если приглашённый ушёл со страницы `/invite`, вход и регистрация
возвращают его к ссылке из письма (§4.3). «Забыли пароль» не меняется — у
приглашённого ещё нет аккаунта.

Ссылка действует **72 часа**. Ссылку ищут по хэшу токена; сам токен, пока
приглашение открыто, хранится в зашифрованном виде (ключ выводится из
`SECRET_KEY`), поэтому админ может **скопировать ссылку в любой момент**
(§3.6). После принятия или отзыва токен удаляется.

Почта при создании проверяется по DNS: домен без почтового сервера (опечатка,
выдуманный домен) → 422 `invitation_email_undeliverable`. В `email_status`
бэкенд сохраняет только синхронный результат попытки отправки (§3.7): провайдер
принял письмо или письмо не было отправлено. Фактическая доставка не отслеживается.

`POST /admin/users` (создание сотрудника с паролем) удалён в PRO-466.
Без админки приглашение создаётся из консоли:
`scripts/create_admin_user.py` / `scripts/create_psychologist_user.py
<email> [--locale ru|kk] [--replace]` печатают `invite_url`. Если на почту
уже есть активное приглашение с той же ролью и языком, перевыпускают его
ссылку; с другой ролью или языком — отказывают, а с `--replace` отзывают
его и создают новое.

## 2. Общее

### 2.1 Статус приглашения

`status` вычисляется на бэкенде из дат, отдельно не хранится. Порядок
проверки — сверху вниз, первое совпадение побеждает:

| `status` | Условие | UI (PRO-464) |
|---|---|---|
| `accepted` | приглашение принято (`accepted_at` задан) | «Принято» |
| `revoked` | отозвано админом (`revoked_at` задан) | «Отозвано» |
| `expired` | `expires_at` наступил | «Истекло» |
| `pending` | всё остальное | «Ожидает» |

Принятое или отозванное приглашение остаётся `accepted` / `revoked` и после
`expires_at`.

### 2.2 Формат ошибок

Ошибки приглашений — `AppError`:

```json
{"detail": "<текст на языке запроса>", "error_code": "invitation_expired"}
```

Ветвиться **только по `error_code`** (`apiErrorCode()` из
`@/shared/api/client.ts`), `detail` не парсить. Текст для пользователя — из
i18n-каталога фронта по коду.

Исключения из этого формата:

- **422** — ошибки валидации тела запроса, pydantic-формат
  `{"detail": [{"type": ..., "msg": ..., "loc": [...]}]}` без `error_code`.
  Для правил этих эндпоинтов `msg` уже на языке запроса, а `type` —
  стабильный код: `invitation_email_invalid`, `invitation_role_invalid`
  (`student` или неизвестная роль), `invitation_locale_invalid`,
  `password_too_short`, `password_letter_required`,
  `password_digit_required`. Фронт проверяет то же самое до отправки.
  Отсутствующее поле — `type: "missing"`, `msg` тоже на языке запроса
  («Обязательное поле» / «Міндетті өріс», для всего API). Исключение —
  422 `invitation_email_undeliverable` (§2.3): обычный `AppError` с
  `error_code`.
- **429** — rate limit, как на остальных `/auth/*`: `{"detail": "..."}`
  **без** `error_code` + заголовок `Retry-After` (секунды). Определять по
  HTTP-статусу.
- **401/403** админских эндпоинтов — как во всей админке.

### 2.3 Коды ошибок

| HTTP | `error_code` | Когда |
|---|---|---|
| 400 | `invitation_invalid` | токена нет в базе: опечатка в ссылке или ссылка заменена через «Отправить повторно»; также принятое приглашение, чей аккаунт с тех пор удалён |
| 400 | `invitation_expired` | срок ссылки истёк |
| 400 | `invitation_revoked` | приглашение отозвано админом |
| 400 | `invitation_used` | приглашение уже принято (аккаунт существует) |
| 404 | `invitation_not_found` | админский эндпоинт: нет приглашения с таким `id` |
| 409 | `user_exists` | на почту уже есть **подтверждённый** аккаунт (любой роли) |
| 409 | `invitation_pending` | на почту уже есть приглашение в статусе `pending` — используйте «Отправить повторно» |
| 409 | `invitation_superseded` | create / resend: пока письмо уходило, приглашение изменил другой запрос (новая ссылка, отзыв, принятие или истечение срока) — ответ с уже недействительной ссылкой не отдаётся |
| 409 | `invitation_link_unavailable` | §3.6: ссылку не восстановить (приглашение старше хранения ссылок или сменился `SECRET_KEY`) — «Отправить повторно» |
| 422 | `invitation_email_undeliverable` | §3.2: домен почты не принимает письма (нет MX/A-записи) |
| 409 | `invited_email_register` | `POST /auth/register` на почту с `pending`-приглашением (§4.3) |

`user_exists` срабатывает только на подтверждённый аккаунт. Неподтверждённый
(кто-то зарегистрировался на эту почту, но не ввёл код) создание приглашения
не блокирует — при принятии такой аккаунт забирается приглашённым (§4.2).

## 3. Админские эндпоинты

### 3.1 Объект приглашения — `AdminInvitationItem`

```jsonc
{
  "id": "7b0c6a3e-2f4d-4e55-9a51-3f0c2a1d9e10",
  "email": "psy@example.com",           // в нижнем регистре
  "role": "psychologist",               // "psychologist" | "admin"
  "locale": "kk",                       // "ru" | "kk" — язык письма; станет users.locale при принятии
  "status": "pending",                  // §2.1
  "invited_by": {                       // null, если пригласивший админ удалён
    "id": "e78dd10f-0527-4bd8-bb83-b4a9bc724287",
    "email": "admin@example.com"
  },
  "created_at": "2026-10-07T09:20:13Z",
  "expires_at": "2026-10-10T09:20:13Z", // после resend — новый срок
  "accepted_at": null,
  "revoked_at": null,
  "email_status": "sent"                // результат последней попытки отправки
}
```

`email_status`:

| Значение | Что значит | Откуда |
|---|---|---|
| `sent` | почтовый провайдер принял письмо к отправке; это не подтверждает доставку | синхронный ответ провайдера |
| `failed` | письмо не ушло: ошибка провайдера или почта не настроена | бэкенд |
| `null` | приглашение создано до сохранения результата отправки | — |

Ответы create и resend — `AdminInvitationSent`: тот же объект плюс два поля:

```jsonc
{
  // ...все поля AdminInvitationItem...
  "invite_url": "https://profile.newlevelhub.kz/invite?token=Zx3...",
  "email_sent": true
}
```

- `invite_url` — для кнопки «Скопировать ссылку». Позже ту же ссылку отдаёт
  §3.6.
- `email_sent: false` (= `email_status: "failed"`) — приглашение создано (или ссылка обновлена), но
  письмо не ушло: почтовый провайдер вернул ошибку или почта на окружении
  не настроена (`RESEND_API_KEY` пуст). Ссылка в лог не пишется. Это **не ошибка запроса** (ответ 201/200):
  показать предупреждение «письмо не отправлено — скопируйте ссылку и
  передайте вручную» и дать скопировать `invite_url`.

### 3.2 Создать приглашение

```text
POST /api/v1/admin/invitations
Authorization: Bearer <admin-token>

{"email": "psy@example.com", "role": "psychologist", "locale": "kk"}
```

- `email` — обязателен, приводится к нижнему регистру.
- `role` — обязателен, `"psychologist"` или `"admin"`. `"student"` → 422.
- `locale` — `"ru"` или `"kk"`, по умолчанию `"ru"`.

| Ответ | Когда |
|---|---|
| **201** `AdminInvitationSent` | создано, письмо отправлено (или см. `email_sent`) |
| 409 `user_exists` | на почту есть подтверждённый аккаунт |
| 409 `invitation_pending` | на почту уже есть `pending`-приглашение |
| 422 `invitation_email_undeliverable` | домен почты не принимает письма — показать у поля email |
| 422 | невалидное тело |

Проверка домена — один DNS-запрос (MX, затем A/AAAA). Если DNS не ответил за
5 секунд, адрес пропускается. Консольные скрипты (§0) домен не проверяют —
они печатают ссылку.

Старые `expired` / `revoked` / `accepted` приглашения на ту же почту
создание не блокируют — появляется новая запись, старые остаются в списке.

### 3.3 Список приглашений

```text
GET /api/v1/admin/invitations?page=1&limit=20&status=pending&search=psy
```

- `page` / `limit` — как везде в админке (с 1, `limit` 1..100, по умолчанию 20).
- `status` — опционален: `pending` / `accepted` / `expired` / `revoked`.
- `search` — опционален, по email: без учёта регистра, частичное совпадение.
- Сортировка фиксирована: `created_at`, новые сверху.

```jsonc
{
  "items": [ /* AdminInvitationItem[] — без invite_url */ ],
  "total": 12,
  "page": 1,
  "limit": 20
}
```

### 3.4 Отправить повторно

```text
POST /api/v1/admin/invitations/{id}/resend
```

Тела нет. Для `pending` и `expired`: в той же записи выпускается новый токен,
`expires_at` = сейчас + 72 часа, уходит новое письмо (на `locale` приглашения).
**Старая ссылка сразу перестаёт работать** (`invitation_invalid`). Истёкшее
приглашение снова становится `pending`.

| Ответ | Когда |
|---|---|
| **200** `AdminInvitationSent` | новая ссылка выпущена |
| 400 `invitation_used` | приглашение уже принято |
| 400 `invitation_revoked` | приглашение отозвано — создайте новое (§3.2) |
| 404 `invitation_not_found` | нет такого `id` |
| 409 `user_exists` | на почту за это время появился подтверждённый аккаунт |
| 409 `invitation_pending` | resend истёкшего, когда на ту же почту уже создано новое `pending`-приглашение |

### 3.5 Отозвать

```text
DELETE /api/v1/admin/invitations/{id}
```

Только для `pending`: ссылка перестаёт работать (`invitation_revoked`),
запись остаётся в списке со статусом `revoked`.

| Ответ | Когда |
|---|---|
| **200** `AdminInvitationItem` | отозвано, в теле — обновлённая строка |
| 400 `invitation_used` | уже принято |
| 400 `invitation_revoked` | уже отозвано |
| 400 `invitation_expired` | уже истекло — отзывать нечего |
| 404 `invitation_not_found` | нет такого `id` |

### 3.6 Ссылка приглашения

```text
GET /api/v1/admin/invitations/{id}/link
```

Только для `pending`. Отдаёт ту же ссылку, что в последнем письме (после
resend — новую).

```jsonc
// 200
{"invite_url": "https://profile.newlevelhub.kz/invite?token=Zx3...", "expires_at": "2026-10-10T09:20:13Z"}
```

| Ответ | Когда |
|---|---|
| **200** `AdminInvitationLink` | ссылка |
| 400 `invitation_used` / `invitation_revoked` / `invitation_expired` | приглашение закрыто — ссылка не работает |
| 404 `invitation_not_found` | нет такого `id` |
| 409 `invitation_link_unavailable` | ссылку не восстановить — «Отправить повторно» |

### 3.7 Границы статуса отправки

Отдельного webhook доставки нет. `email_status` фиксирует только результат
непосредственного вызова почтового провайдера: `sent` означает «принято к
отправке», а не «доставлено получателю». Если администратору нужно гарантировать
получение, он копирует `invite_url` и передаёт его сотруднику другим каналом.

## 4. Публичные эндпоинты (страница `/invite`)

Токен берётся из query-параметра ссылки: `/invite?token=<token>`. Оба
эндпоинта без авторизации, с rate limit по IP (429, §2.2): §4.1 — 30
запросов, §4.2 — 10 запросов за 15 минут. Считаются все запросы, включая
успешные.

Проверки токена в обоих эндпоинтах идут в одном порядке:
`invitation_invalid` → `invitation_used` → `invitation_revoked` →
`invitation_expired` → `user_exists`.

### 4.1 Проверить ссылку

```text
GET /api/v1/auth/invitations/{token}
```

```jsonc
// 200
{
  "email": "psy@example.com",
  "role": "psychologist",                // "psychologist" | "admin"
  "locale": "kk",                        // язык приглашения — справочно
  "expires_at": "2026-10-10T09:20:13Z"
}
```

Ошибки: 400 `invitation_invalid` / `invitation_expired` /
`invitation_revoked` / `invitation_used`, 409 `user_exists`, 429.

### 4.2 Принять

```text
POST /api/v1/auth/invitations/accept

{"token": "Zx3...", "password": "Testpass123"}
```

- `password` — те же правила, что при регистрации: минимум 8 символов, хотя бы
  одна буква и одна цифра. Нарушение → 422.

Успех — **200**, `TokenResponse`, как у `/auth/login`:

```jsonc
{
  "access_token": "eyJ...",
  "token_type": "bearer",
  "user": {
    "id": "...",
    "email": "psy@example.com",
    "role": "psychologist",
    "is_admin": false,
    "locale": "kk"                       // из приглашения
  }
}
```

Сохранить токен так же, как после логина, и перейти по `homePathForUser`.

Что происходит на бэкенде:

- аккаунта на почту нет → создаётся с ролью и языком из приглашения, почта
  считается подтверждённой;
- есть **неподтверждённый** аккаунт → он забирается: пароль заменяется, роль
  из приглашения, почта подтверждена, старые сессии этого аккаунта
  разлогиниваются;
- приглашение становится `accepted`. Два одновременных accept с одним токеном
  проходят не оба: второй получит `invitation_used`.

Ошибки: 400 `invitation_invalid` / `invitation_expired` /
`invitation_revoked` / `invitation_used`, 409 `user_exists`, 422, 429.

### 4.3 Вход, регистрация и подтверждение почты

Аккаунт приглашённого создаётся по ссылке. Чтобы человек, ушедший с
`/invite`, не застрял, остальные экраны входа знают о `pending`-приглашении:

| Эндпоинт | Аккаунта нет, есть `pending`-приглашение |
|---|---|
| `POST /auth/login` | **403** `{"detail": {"detail": "invitation_pending", "email": "<почта>"}}` — в том же формате, что `google_account` / `email_not_verified`; считается неудачной попыткой входа (rate limit) |
| `POST /auth/register` | **409** `invited_email_register` (`AppError`); аккаунт не создаётся |
| `POST /auth/verify-email` | у **неподтверждённого** аккаунта на эту почту код принимает приглашение: роль и язык из приглашения, приглашение `accepted` (как Google, §5) |

Истёкшее или отозванное приглашение на эти эндпоинты не влияет.

## 5. Вход через Google (`POST /api/v1/auth/google`)

Запрос и ответ (`TokenResponse`) **не меняются**. Новое: если на почту
Google-аккаунта есть `pending`-приглашение, вход его принимает.

| Аккаунт на эту почту | Есть `pending`-приглашение | Результат |
|---|---|---|
| нет | да | создаётся с ролью и языком из приглашения, приглашение `accepted` |
| неподтверждённый | да | забирается, роль из приглашения, приглашение `accepted` |
| подтверждённый | да | обычный вход, роль **не меняется**, приглашение остаётся `pending` |
| любой | нет (или истекло / отозвано) | как раньше: новый аккаунт — `student` |

Для страницы `/invite`:

- Кнопку «Войти через Google» показывать только после успешного §4.1.
- Приглашение принимается, только если почта выбранного Google-аккаунта
  совпадает с приглашённой. После ответа сравнить `user.email` с `email` из
  §4.1: если не совпало, приглашение **не принято** (пользователь вошёл под
  другим аккаунтом, возможно, только что созданным `student`) — показать это
  явно, а не молча перекидывать в кабинет ученика.

## 6. Что построить на фронте

**PRO-464 — админка:**

1. Форма «Пригласить»: email, роль (`psychologist` / `admin`), язык письма
   (`ru` / `kk`). Заменяет `CreateStaffModal` с паролем.
2. Таблица: email, роль, `invited_by.email`, `created_at`, статус (§2.1),
   фильтр по статусу, поиск по email, пагинация.
3. Действия по статусу:
   - `pending` — «Ссылка» (§3.6), «Отправить повторно», «Отозвать»;
   - `expired` — «Отправить повторно»;
   - `accepted` / `revoked` — нет действий.
4. После create / resend — показать «Скопировать ссылку» с `invite_url`; при
   `email_sent: false` — предупреждение (§3.1). В списке — `email_status`.
5. Сообщения для 409 `user_exists` и `invitation_pending` (для последнего —
   подсказать «Отправить повторно»).

**PRO-465 — страница `/invite?token=...`:**

1. На загрузке — §4.1; почта показывается и не редактируется.
2. Пароль + повтор пароля с подсказками по сложности → §4.2 → сохранить JWT →
   `homePathForUser`.
