# Как генерируется контент roadmap-плана — по каждому полю

Дата: 2026-08-05. Основано на прямом чтении `app/prompts/direction_roadmap.py`
и `app/services/roadmap_builder.py` — не пересказ, а точные цитаты с номерами
строк.

Общий принцип на весь модуль (докстринг `direction_roadmap.py:1-19`): **два
слоя, специально разделены**. Реальные курируемые факты (какие профессии есть
в направлении, вес предметов, требования вузов) лежат в БД и подставляются
`roadmap_builder.py` напрямую — LLM их не трогает вообще. LLM отвечает только
за тонкий персонализирующий слой поверх — текст `why`/`note`/`growth_focus`
плюс запасной вариант `starter_actions`, если нет курируемого.

Раньше промпт просил LLM придумать полный 4-этапный план на 12 месяцев
целиком — тестирование на реальных аккаунтах показало 2 проблемы: модель
выдавала ложную уверенность (называла одну профессию, хотя данные её не
выделяли) и шаги съезжали в абстракции ("собери команду") вместо конкретики.
Текущий промпт — прямой ответ на оба этих провала.

---

## `profession_options[].why` и количество профессий [обновлено TASK #10]

Правило по `why` (`direction_roadmap.py`, раздел "ПРАВИЛО ПО why"):
заполняется, только если есть сигнал, который различает КОНКРЕТНО одну
профессию среди остальных **в текущем ответе** — не сигнал "нравится это
направление вообще". Пример из промпта: сильная визуально-дизайнерская ось
при выборе между Frontend и Backend. Модели прямо запрещено писать `why`,
который на самом деле не различает — "тогда лучше null". Это правило
**не менялось** задачей #10 — расширение количества профессий не означает
послабление честности `why`.

Количество профессий теперь зависит от `goal` (`direction_roadmap.
profession_option_bounds`, единый источник истины для промпта и для
`_valid_plan`):

| `goal` | Диапазон | Комментарий |
|---|---|---|
| `profession` | 3-5 | Ограничено реальным размером `profession_list` направления — если профессий физически меньше 3, вернутся все, что есть (тот же принцип честности, что и у `why`) |
| любая другая цель | 1-3 | Как было до задачи #10 |

Название профессии модель обязана взять словом в слово из `profession_list`
— не может придумать новую. Точное целевое число (`min`/`max`) передаётся
модели явно в `profession_options_target` внутри блока НАПРАВЛЕНИЕ — модель
не обязана сама считать длину `profession_list` и выводить диапазон.

## `profession_options[].practice` [новое, TASK #10]

Заполняется **только когда `goal == "profession"`** — 1-2 элемента
`RoadmapTask` на каждую профессию в ответе. От модели требуется только
`text` (одно предложение, один из двух жанров: "как попробовать эту
профессию на практике" или "какой курс пройти / в какой кружок вступить" —
с теми же правилами платформ/офлайн-кружков, что и у `starter_actions`
ниже). `category` (всегда `"practice"`), `priority` (по порядку с 1) и
`resources` (всегда `[]`) — backend-присваиваемые
(`roadmap_builder._practice_for`), не решение модели.

Для любой другой цели (`explore`/`unsure`/`university`/`known`) —
`practice` обязан быть `[]` для каждой профессии, это тоже часть
`_valid_plan`'а структурной проверки, не просто пожелание в тексте промпта.

## `subjects_now[].note`

Даётся ровно по одной заметке на каждый предмет из `subjects_required`
направления (не больше, не меньше — это одно из условий `_valid_plan`).
Источник персонализации — приоритетная цепочка, сверху вниз, до первого
непустого (`direction_roadmap.py:109-118`):

1. **`subject_readiness`** — реальный результат мини-квиза по предмету
   (`is_strength`/`level`/`interest`) — если квиз пройден, используется он.
2. **Самоотчёт** — `subjects_easy`/`subjects_hard`/`subjects_liked`/
   `subjects_disliked` — если мини-квиза по этому предмету не было.
3. **Нейтральная заметка** без выдумки уровня ("этот предмет входит в
   программу направления") — если сигнала вообще нет.

`weight` (число) в эту логику не входит — он добавляется системой отдельно
из `Direction.subjects_required`, LLM его не видит и не может повлиять.

## `starter_actions`

Двухуровневая логика, но **первый уровень вообще не LLM**
(`roadmap_builder.py:268-271`, `_starter_actions_for`):

```python
def _starter_actions_for(direction, plan):
    curated = list(direction.first_steps or [])
    return curated if curated else list(plan.starter_actions)
```

Если у направления есть курируемый `Direction.first_steps` — используется он
целиком, LLM-версия просто выбрасывается (даже не отправляется в ответ). Если
курируемого списка нет — идёт LLM-фолбэк со следующими правилами
(`direction_roadmap.py:120-153`):

- 2-3 действия, каждое — одно предложение, не абзац.
- Каждое действие должно быть выполнимо **одним** учеником — явно запрещены
  "собери команду", "найди единомышленников", "организуй кружок". Можно
  вступить в уже существующий кружок, участвовать в чужом мероприятии,
  заниматься самостоятельно.
- Глубина зависит от возраста: 10-13 лет — просто, без жаргона; 14-15 —
  конкретные темы; 16-17 — профильная подготовка, олимпиады, портфолио.
- **[TASK #9] Для `goal in (explore, unsure)`** промпт дополнительно
  подсказывает модели предпочитать формулировки из явного списка клиента:
  пробный/вводный курс, пробное занятие или вступление в уже существующий
  кружок, дебаты/дискуссионный клуб, маленький пробный проект, поиск
  возможности поговорить с человеком этой профессии (без выдуманных имён
  и организаций), олимпиадные задачи, лекции/видео. Это подсказка по
  формулировкам, не отдельная структурная проверка — количество (2-3) и все
  ограничения ниже (платформы, "один ученик", возраст) не изменились. Для
  остальных целей секция промпта про "ПОНЯТЬ СЕБЯ" не задействуется.
- **Разрешённые платформы — закрытый список**, ничего за его пределами
  придумывать нельзя (`direction_roadmap.py:140-148`): Stepik, ЯКласс, Khan
  Academy, Открытое образование (openedu.ru), Хекслет, Постнаука, Arzamas,
  N+1, Coursera (только audit-режим), GitHub. Модели явно запрещено выдумывать
  название конкретного курса/книги/кружка/организации и давать ссылки — можно
  называть только платформу целиком ("пройди вводный курс по Python на
  Stepik"), не выдуманный курс на ней. Офлайн-кружки — без названия
  организации ("найди в своём городе кружок робототехники").

Если у ученика есть релевантный артефакт (кружок/хобби/книга/игра, указанный
при онбординге) — предпочтение отдаётся действию, которое развивает именно
его, а не абстрактно новому (`direction_roadmap.py:211-214`).

## `growth_focus`

Промпт называет это "САМОЕ ОТВЕТСТВЕННОЕ МЕСТО" (`direction_roadmap.py:155`)
— здесь запрещено достраивать правдоподобную слабость, работает только то,
что подтверждено данными. Приоритетная цепочка из 5 источников, сверху вниз,
до первого непустого/релевантного (`direction_roadmap.py:159-175`):

1. **`subject_readiness`** с `is_strength=false` — измеренный (не
   самоотчётный) пробел по нужному направлению предмету. Самый сильный сигнал.
2. **`axis_growth_areas`** — измеренный сигнал по осям направления, но ниже
   порога.
3. **`subjects_hard`/`subjects_disliked`** — самоотчёт, но только если предмет
   реально нужен направлению (химия не берётся для backend-разработчика).
4. **`rejected_directions`** — направления, которые ученик явно отклонил в
   тесте; если отклонённое направление держалось на чём-то нужном и текущему,
   но выраженном здесь слабее.
5. **`axis_profile` направления вне strengths** — ось значима направлению, но
   не вошла в сильные стороны (не отрицательная, просто ниже порога).

Источники 1-2 — измеренные, 3-5 — самоотчёт/косвенные. Берётся **один**
источник с максимальным приоритетом из непустых, смешивать запрещено. В
`evidence` модель обязана назвать конкретный сигнал — если подставить нечего,
значит слабость выдумана, так делать нельзя (`direction_roadmap.py:180-184`).

**Если ни один из 5 источников не даёт релевантного сигнала** (реальный случай
из вашего примера с архитектором выше в этом чате) — модели запрещено
изобретать слабость (запрещены "публичные выступления"/"прокрастинация" без
основания в данных). Вместо этого берётся источник 5, но переформулированный
как **зона усиления следующего уровня**, а не недостаток — именно так
выглядел ответ "нет выраженных слабых мест по ключевым осям" в примере с
архитектором (`direction_roadmap.py:186-192`).

Точка роста не может быть профильным навыком направления (не
"программирование" для IT) — `direction_roadmap.py:194-196`.

## `skills_to_build`

Минимально регламентировано: 3-6 коротких тегов, без описаний
(`direction_roadmap.py:198-200`). Единственное явное ограничение — количество
и формат, содержательных приоритетов/источников для этого поля в промпте нет.

## `university_requirements`

**Не LLM вообще, ни в каком виде.** Полностью собирается в
`roadmap_builder._university_requirements_for` из реальных `Program` строк —
`exams`, `application_deadline`, `grants`, `language_level`, `portfolio_needed`,
`required_documents`. LLM даже не видит эти данные в промпте.

## `artifacts` (хобби/кружки/цели ученика) — как влияют на остальные поля

Слабый самоотчётный сигнал, используется избирательно (`direction_roadmap.py:
202-219`):

- **`profession_options.why`**: артефакт с `type=profession`, буквально
  совпадающий с одной из профессий списка — дополнительный (не единственный)
  довод, можно упомянуть в `why` наравне с другими сигналами.
- **`starter_actions`**: релевантный артефакт предпочитается как основа
  действия вместо абстрактно нового.
- **`type=dream`/`type=goal`**, совпадающий по смыслу — может стать
  мотивационной привязкой в одном из `starter_actions`.
- **`growth_focus`**: артефакты **запрещено** использовать вообще ни при каких
  условиях — точка роста берётся только из 5 источников выше
  (`direction_roadmap.py:217-219`).

## `stages` — ⚠️ контент не генерируется вообще, нигде

В отличие от всех полей выше, у `stages` **нет ни LLM-логики, ни
приоритетных цепочек, ни фолбэков** — потому что нет вообще никакой логики.
Единственное место в коде, которое трогает это поле
(`roadmap_builder.py:417`):

```python
roadmap.stages = [m.model_dump() for m in build_empty_horizon_milestones()]
```

`build_empty_horizon_milestones()` (`app/schemas/roadmap.py`) — чистая
функция без аргументов, всегда возвращает одни и те же 5 горизонтов с пустым
`tasks: []`. Она вызывается безусловно при каждой (пере)генерации, без каких
-либо условий на `goal`, направление или сигнал ученика. Это не баг и не
недоделанный фолбэк — это буквально единственное, что сейчас существует для
этого поля.

**Важный момент, который стоит явно признать**: заполнение `stages[].tasks`
контентом **не назначено ни одной существующей задаче в трекере явно**.
Задачи #9 ("explore-генератор — попробовать разное") и #10 ("3-5 профессий
и практика по каждой") — про `profession_options`/подбор направлений, не про
временную раскладку действий по горизонтам 1/3/6/12 месяцев/до поступления.
Контракт-документ (`docs/roadmap-goal-contract.md`) предполагает, что #9/#10
"зальют" `stages`, но по факту их описания этого не покрывают — это отдельный,
пока никем не заведённый кусок работы: логика, которая берёт уже
сгенерированные `starter_actions`/`growth_focus`/`profession_options` (или
генерирует новые задачи) и раскладывает их по 5 горизонтам с учётом `goal`.

## Структурные гарантии (не про содержание, про валидность)

- До 2 попыток генерации (`_MAX_PLAN_ATTEMPTS = 2`, `roadmap_builder.py`) —
  если LLM вернула невалидный JSON или нарушила структуру (`_valid_plan`:
  число профессий вне диапазона для этой `goal` — 3-5 для `profession`, иначе
  1-3, см. `profession_option_bounds` — дубли, `practice` вне 1-2 элементов
  для `profession` / непустой для остальных целей, `subjects_now` не
  покрывает точно все требуемые предметы, `starter_actions` вне 2-3),
  отправляется корректирующая подсказка (`direction_roadmap.
  build_retry_hint(direction, goal)` — текст подстраивается под точный
  диапазон и правило `practice` для этой цели, раньше был статичный словарь
  `RETRY_HINT`) и делается вторая попытка. Если не помогло — 503 "ИИ
  временно недоступен", не отдаётся частично невалидный план.
