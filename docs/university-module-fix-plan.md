# План закрытия пробелов в университетском модуле

Сводный план по итогам разбора карточки `/results/directions/.../universities/:id` — что не так, почему, и что делать. Каждый пункт независим от других (можно распределять параллельно), кроме отмеченных зависимостей. Все цифры и находки проверены напрямую в коде/БД/официальном PDF-источнике, не предположения.

## Поток A — Бэкенд: данные по Казахстану

### A1. Колонка `University.ovpo_code` + применение готового мэтчинга
**Что делать:** миграция — добавить `ovpo_code: str | None, unique, indexed` на `University`. Применить сопоставления из `docs/ovpo-registry-gap-analysis.md`: 31 точное совпадение сразу, 12 вручную найденных — после проверки по списку в том же файле. Починить дубль: `kazatu` (Астана) и `kazahskij-agrotehnicheskij-universitet-kazatu` (Алматы) — оба претендуют на код 002, реальный вуз один и в Астане, вторую строку нужно либо удалить, либо это другой вуз — проверить.

**Почему:** сейчас сопоставление с грантовым PDF МОН РК идёт по строковому имени (`LEGACY_NAME_BY_SLUG` — хардкод-таблица алиасов), это хрупко и является прямой причиной, почему 27 из 64 вузов не получили баллы — не потому что данных нет, а потому что имя в нашей БД не совпало со строкой в источнике. `ovpo_code` — официальный уникальный идентификатор, использовать его вместо мэтчинга по строке закрывает проблему навсегда, а не на один раз.

**Источник:** `scripts/data/ovpo_registry_2026.json` (транскрибирован из легенды `_СПИСОК_ОБЛАДАТЕЛЕЙ_ОБРАЗОВАТЕЛЬНЫХ_ГРАНТОВ_НА_2026_2027_УЧЕБНЫЙ.pdf`).

### A2. Добить грантовые баллы/пороги для оставшихся вузов — ОБЪЕДИНЕНО С A9
**Статус (2026-08-19):** сырые баллы уже извлечены из всего PDF (1656 страниц, безопасно через чанкованные подпроцессы — прямой прогон через один процесс дважды подвесил память/ноутбук, см. `scripts/extract_grant_scores_2026.py` + `scripts/run_grant_extraction_chunked.py`) → `scripts/data/grant_scores_2026_clean.json`, 1902 чистые группы (специальность-классификатор × квота × ОВПО), 43853 получателя, отфильтровано от 38% брака (сбитые колонки таблицы на части страниц). 1005 групп относятся к нашим 44 уже закодированным вузам.

**Дальше упёрлись в то же, что и A9:** специальность в PDF — это код классификатора МОН РК (широкая категория, «Информационные технологии», «Журналистика и репортерское дело»), а не `Program.name` (конкретная специальность вуза) — один-в-один не матчится без официального кросс-справочника специальность→классификатор. Плюс нашли баг данных: у ЕНУ (013) и КазАТУ (002) `Program.name` — это вообще названия факультетов, а не специальностей (баг исходного скрейпа) — для них мэтчинг невозможен в принципе без пересборки специальностей.

**Решение (по итогам обсуждения):** не матчить в лоб (риск приписать балл не той программе выше, чем польза от лишних данных). Объединено с A9 — оба пункта упираются в один и тот же недостающий кросс-справочник специальность→код классификатора, решать одним проходом, не двумя параллельными.

### A3. Догрузка 40+ отсутствующих вузов — ГОТОВО (2026-08-19)
**Сделано:** все 48 вузов из чек-листа `docs/university-data-intake-format.md` исследованы (веб-ресёрч по 6 партиям, `university-data/missing_kz_universities_data.py`) и заведены в БД через расширенный `seed_kz_universities.py` (теперь ищет по `ovpo_code` в приоритете, как канонический ключ, а не только по slug). KZ-вузов в БД было 63, стало **112**. Программ было 2021, стало 2439 (+418, после расширения `specialty_profession_map.py` на 102 новые специальности — см. A9).

**Найдено и починено по пути:**
- Скрытая дыра в `seed_kz_universities.py`: дедуп программ внутри вуза шёл по точному совпадению `Program.name`, а не по `name_normalized` (тому самому полю из A8) — приводило к 500-й на уникальном индексе, когда новая специальность текстово отличалась от уже существующей записи только суффиксом уровня («Биология» vs «Биология (бакалавр)»). Поправлено — теперь матчинг идёт по `name_normalized`.
- Несколько вузов в исходных данных дублировали одну специальность в двух разных группах — добавлена защита от дубля в рамках одного вуза за прогон.
- Код 143 (Университет им. Жубанова/Жумабека Ташенева) — расхождение написания между чек-листом и офсайтом, оставлено как в чек-листе, помечено для ручной проверки.

**Осталось по этому вузовскому пулу:** профильные пары ЕНТ и баллы гранта — это A9/A2, не A3.

### A5. Числовой рейтинг — починить регэксп
**Что делать:** в `seed_92_professions_universities.py` функция `parse_ranking()` ловит только ведущее `#N`. Расширить, чтобы ловила `Топ-N`, ведущее `N+`/`N` в начале строки.

**Почему:** **41 из 109** вузов кластерного датасета имеют текстовый `ranking_label` (например `"1201+ (QS World)"`, `"Топ-5 в мире по CS"`), но `ranking:int = NULL`, потому что регэксп их не парсит — это значит сортировка/фильтр по рейтингу молча теряет треть записей, у которых рейтинг на самом деле есть. Чисто инженерная правка, без новых данных.

### A6. Числовая стоимость обучения — ГОТОВО
**Сделано:** `Program.cost_per_year_min/max/cost_currency` (миграция `a27baccf4197`) + `scripts/parse_cost_label.py` (парсер) + `scripts/backfill_cost_range.py` (бэкфилл). Осознанно консервативный парсер — принимает число только если в тексте ровно одна годовая сумма без второй, конфликтующей (второй уровень программы, расходы на проживание, курс конвертации в скобках — реальная текущая проблема данных, поймал на тестах: «26 000 CNY (≈3 600 USD)» чуть не ушло как USD вместо CNY, поправил на извлечение валюты именно из текста рядом с числом, а не по всей строке).

**Результат:** 612 из 1653 программ (37%) — 16 из точного `cost_per_year` (KZT), 596 распарсено из `cost_label` (65% от 920 текстов с ценой). Остальные 1041 — осознанно пропущены (второй смысл в тексте, семестровая сумма без годового эквивалента, «бесплатно + отдельный сбор») — не гадаем, если есть риск ошибиться.

### A7. Провенанс факта (`fact_sources`) — схема готова, наполнение по ходу
**Сделано:** `Program.fact_sources`/`University.fact_sources` (JSONB, миграция `a27baccf4197`) — `{имя_поля: {"url": ..., "checked_at": "YYYY-MM-DD"}}`. Отдельно от уже существующего построчного `source_url` (тот теперь описан как «на что полагаться, если для конкретного поля точного источника ещё нет» — большинство строк уже трогали несколько сид-скриптов, так что построчный source_url всё равно не привязан к конкретному факту).

**Осталось:** это не бэкфилл прошлых данных (большинство существующих фактов не будет иметь записи — отсутствие ключа значит «источник неизвестен», не «непроверено») — это инфраструктура на будущее. Начиная с A3/A9/A4 (новый ресёрч) — писать сюда, не оставлять как раньше.

### A8. Нормализация имён программ + уникальный индекс — ГОТОВО
**Сделано:** `Program.name_normalized` (DB-generated, нижний регистр, без суффиксов вида «(бакалавр)»/«(магистратура)», без лишних пробелов) с уникальным индексом `(university_id, name_normalized)` — уже в схеме. При заведении A3 обнаружилось, что не все сид-скрипты сверяются с этим полем при поиске дубля (см. находку в A3) — сама колонка и индекс были готовы, использовалась не везде.

### A9. Профильные пары ЕНТ по специальностям + мэтчинг баллов гранта (A2 объединён сюда)
**Зависит от A3 — A3 готово, эта часть по-прежнему открыта.**

**Не путать со сделанным:** после A3 отдельно дополнен `scripts/specialty_profession_map.py` (+102 новые специальности → 580 всего) — это маппинг «специальность вуза → профессия платформы» (нужен, чтобы Program вообще привязался к Direction), другой кросс-справочник, не имеет отношения к профильным парам ЕНТ/классификатору МОН РК ниже. 34 специальности из 48 новых вузов остались непокрыты этим маппингом намеренно (слишком общие/административные — "Педагогика" без предмета, "Резидентура" и т.п.), видно в `unmapped`-отчёте `seed_kz_universities.py`.

**Что делать:** LLM-ресёрч по сайтам новых вузов (A3) даёт только общий шаблон — «История Казахстана, Математическая грамотность, Грамотность чтения + профильные предметы в зависимости от специальности» — без реальной предметной пары, потому что эта пара не является атрибутом конкретного вуза, а задаётся государственным классификатором специальностей МОН РК (тот же класс источника, что уже используется в A2 для грантового PDF). Нужно: по каждой специальности новых вузов найти код специальности в классификаторе и подставить реальную профильную пару оттуда, а не с сайта вуза.

**Почему отдельным шагом, не частью A3:** веб-ресёрч по сайту вуза для этого поля структурно не работает — сайты в лучшем случае повторяют тот же общий шаблон, что уже видно на первой обработанной партии (8 вузов, коды 004/005/008/009/010/011/014/015) — `admission_requirements` у всех получился почти одинаковым текстом. Значит для этого поля нужен не ресёрч по сайту, а мэтчинг специальности → классификатор, отдельным проходом после того, как специальности вуза уже известны из A3.

## Поток C — Фронтенд: подключение уже готовых данных бэкенда

### C1. Обновить TS-типы
**Файл:** `Profy-Frontend/src/shared/types/index.ts`. Сейчас `ProgramDetail` не знает о поле `requirements_summary` (готовая типизированная структура — `min_ent_threshold`, `admission_scores_2026`, `exams`, `language_level`, `portfolio_needed`, `required_documents`, `min_gpa`, `min_sat`, `extracurriculars`, `notes`), `DirectionRoadmapResponse` не знает о `university_requirements[]`. `UniversityBrief` не хватает `short_name`, `aliases`, `location`, `ranking_label`, `uniranks_kz_rank`, `uniranks_world_rank`, `uniranks_note` — бэкенд их уже отдаёт (`app/schemas/university.py`), фронт их просто отбрасывает.

**Почему первый шаг:** это чистое подключение уже существующих на бэкенде данных, без единой новой строчки бэкенд-кода — самая дешёвая по эффекту правка во всём плане.

### C2. Карточка требований — KZ-трек
**Развилка по `university.country === 'Казахстан'`.**
- Три обязательных предмета ЕНТ (История Казахстана, Математическая грамотность, Грамотность чтения) — **захардкодить константой в UI**, не тянуть из данных (это неизменный факт системы ЕНТ, а не атрибут конкретного вуза).
- Профильная пара — из `requirements_summary.exams`, скрывать блок, если массив пуст или содержит только литеральное `"ЕНТ"` без реальных предметов (таких сейчас 8 из 377 — редкий, но встречающийся мусор).
- Баллы — два раздельных, никогда не смешивать в один лейбл:
  - Есть `admission_scores_2026` → **«Балл гранта 2026/2027: 91–139»** (диапазон мин–макс, можно добавить квоту).
  - Нет, но есть `min_ent_threshold` → **«Минимальный порог ЕНТ: 60+»**.
  - Нет ни того, ни другого → «баллы пока не подтверждены» (это цель бэкфилла A2, не постоянное состояние UI).

### C3. Карточка требований — International-трек
- Язык обучения + требуемый сертификат (`language_level`/`min_ielts`).
- Чек-лист «что нужно подготовить»: эссе / рекомендательные письма / собеседование / портфолио — рендерить **только пункты со значением `true`** (список того, что нужно), никогда не показывать `false`/отсутствие как вычеркнутый пункт — это разные состояния («точно не нужно» вообще не бывает известно у большей части текущих данных, `None` ≠ `false`).
- Стоимость — диапазон текстом (`cost_label`), пока нет числа (см. A6).
- Ссылка на сайт вуза — как основной источник, когда собственных структурированных данных не хватает.

### C4. Полностью убрать дедлайн и сырой JSON-дамп
- **Дедлайн (`application_deadline`/`deadlines.application_close`) — не рендерить вообще.** Затрагивает 16 из 1659 программ, все даты — одноразовые записи 2026 года, часть уже в прошлом (сегодня 2026-08-19, а есть даты вроде `2026-02-28`, `2026-07-07`). Никакого механизма ежегодного обновления сейчас нет — показывать нечего. Вернуть поле, когда/если появится процесс с ежегодным рефрешем вместе с баллами гранта.
- Никогда не рендерить `program.requirements`/`notes` как сырой key-value дамп (текущее поведение `RequirementsTable`/`DeadlinesGrid`) — только через типизированный `requirements_summary`.

### C5. Индикатор достоверности
Небольшой бейдж на карточке («баллы подтверждены МОН РК 2026» / «данные приблизительные» / «уточняйте на сайте вуза»), вычисляемый из того, какие поля `requirements_summary` реально заполнены у конкретной программы — не даёт всем карточкам выглядеть одинаково надёжными, когда по факту часть — один абзац текста.
